## 0. 一句话

微信**不发支付通知**，所以这条路只能是：

> 用户自己点开账单详情页 → App 读屏 → 解析 → 生成草稿

这是**半自动**，不是"微信一付款就自动记"。理解这一点决定了它在产品上是什么东西。

---

## 1. 为什么只能走读屏

### 通知栏这条路对微信物理上不通

- 系统 `notification_enqueue` 日志在付款时段**零条**支付通知
- 实测收到的微信通知内容是聊天消息：`收到 com.tencent.mm 的通知：H。|我送审|`
- 结论：微信支付成功不产生可供读屏监听的通知

### 账单详情页是唯一稳定的入口

用户录屏（OPPO PMA110，小布记忆）显示稳定触发的页面是**用户主动点进历史流水的账单详情页**，不是付款成功页。原因：

| | 付款成功页 | 账单详情页 |
|---|---|---|
| 存在时长 | 一两秒，瞬态 Activity | 稳定，可随时回看 |
| 易被吃掉 | 是（支付保护 + 动画） | 否 |
| 字段 | 不全 | 含**交易单号**、支付时间、商户全称 |

代价是必须能认得出「这笔我见过了」——这正是第 4 道关卡存在的理由。

## 2. 读取机制（`KapiAccessibilityService.kt`）

### 2.1 拿根节点

```kotlin
val root = rootInActiveWindow
```

无障碍服务在每次界面变化时把**当前活跃窗口的整棵节点树**交出来。

**微信不屏蔽这棵树**——这是实测推翻了旧结论的关键点。

> ### 曾经写错过：微信屏蔽读屏
>
> 旧结论「微信/支付宝会调 `setImportantForAccessibility(NO)` 屏蔽子树」是**错的**。
>
> 错因是测法：三轮「拉起微信」都用
> `adb shell monkey -p com.tencent.mm -c LAUNCHER 1`，
> 而 App 已经在前台时 `monkey` **不产生窗口切换事件**，无障碍只在界面变化时回调。
> 拿着自己造出来的 0 条事件，断言了「对方屏蔽读屏」。
>
> 正解：`am start -n <pkg>/<activity>` 会真的产生 `WINDOW_STATE_CHANGED`。
> 实测微信冷启动读到 **88 个节点**；工行/招行/交行/中行/云闪付/支付宝同样可读。

### 2.2 核对包名（关键防线）

```kotlin
if (rootPkg != null && rootPkg != eventPkg) return null
```

- `event.packageName` = **事件声称的** App
- `rootInActiveWindow` = **屏幕上实际画着的**

App 刚切换、窗口没画完时两者会不一致。实测现场：

```
22:55:52.933  事件 com.icbc      形状像一笔：88 个节点（已支付¥13.00）
22:55:52.987  事件 com.tencent.mm 形状像一笔：88 个节点（已支付¥13.00）
```

同一屏内容被记成两个来源。**危险在于它不报错**——工行那笔被当成微信的账走完了全流程，只靠指纹去重侥幸挡下。换个金额、换一屏、或事件晚半秒到达，就是一条凭空多出来的假账。

> 宁可漏一次（用户自己会补），不能记错一次（假账污染统计且用户不会发现）。

### 2.3 显式栈遍历，只取文字

```kotlin
val stack = ArrayDeque<AccessibilityNodeInfo>()
stack.addLast(root)
while (stack.isNotEmpty()) {
    if (visited++ > MAX_NODES || out.size > MAX_NODES_TOTAL) break
    val node = stack.removeLast() ?: continue
    val label = node.text?.toString()?.trim()
    if (!label.isNullOrEmpty()) out.add(Node(label))
    val content = node.contentDescription?.toString()?.trim()
    if (!content.isNullOrEmpty() && content != label) out.add(Node(content))
    for (i in 0 until node.childCount) node.getChild(i)?.let { stack.addLast(it) }
}
```

| 设计 | 原因 |
|---|---|
| **只用 text + contentDescription，不取坐标** | 上一版按金额节点邻域裁剪，坐标从 `uiautomator dump` 抄的——dump 的节点划分和原始树**不一样**（它把「转账成功」和「1.00」拆成两个节点，原始树合在一起），真机上**一次都没触发过** |
| **显式栈不递归** | 某些 App 节点树很深，递归会真爆栈 |
| `MAX_NODES = 400` | 微信会话列表几千节点，回调在主线程，掉帧就是用户看到卡住 |
| 去抖 `COOLDOWN_MS = 1.5s` | 支付页连续重绘一秒能来十几次事件 |

### 2.4 延迟重读（补半屏）

窗口切换那一瞬读到的是半屏（详情页还在 `加载中`）。`TYPE_WINDOW_STATE_CHANGED` 时延迟 **1.2 秒**、**切回主线程**再读一次。

```kotlin
scope.launch {
    delay(SETTLE_DELAY_MS)          // 1_200ms
    withContext(Dispatchers.Main.immediate) {
        readScreen(pkg, System.currentTimeMillis())
    }
}
```

- **为什么 1.2s**：转场动画 300ms 内结束，但「交易单号 / 商户单号」几行是**异步补齐**的，实测 1~2 秒才稳定
- **为什么必须切主线程**：赌 `rootInActiveWindow` 跨线程可用，赌输了是**静默**的——`collectTexts` 的 `catch(Throwable)` 会把它变成一条「无障碍对微信无效」的日志，而那条结论早被推翻了，会再次把排查引到错误方向
- **去抖名额只在真的派发捕获时才占**：判成「不是一笔」的那一屏，不该拦住紧接着打开的下一屏——那正是列表页 → 详情页的必经之路

### 2.5 只读不写（硬约束）

这个类里**不存在任何** `performAction` / `dispatchGesture`。

- 隐私：记账 App 不是脚本工具，一个能点按钮的无障碍服务，能力上和「自动下单」只差一步
- 平台规则：Google Play 禁止无障碍服务「自主发起、规划及执行动作」，明确允许「确定性的、基于规则的自动化」

只读落在允许这一侧，能点落在禁止这一侧。走侧载分发不影响判断，但这条路以后想上架，差别就在这一个决定上。

## 3. 节点顺序：值在标签前

遍历出来的**原始顺序**（日志 23:34:10 原文）：

```
加载中 | 本服务由财付通提供 | 商家电话 | 申请电子凭证 | 在此商户的交易
| 发起群收款 | 对订单有疑惑 | 账单服务 | 商家小程序 象子茶铺
| T1312174297162407936 | 商户单号
| 4500000488202609303522863079 | 交易单号
| 支付方式 | 零钱 | … | -13.00
```

**截图上明明是左标签右值，树遍历出来是反的。**

### 旧实现为什么静默失效

```kotlin
Regex("""(?:微信支付)?交易单号\s*[:：]?\s*([A-Za-z0-9]{12,})""")
```

假设「标签后面紧跟数字」：

- `交易单号` 后面是「支付方式」→ **匹配不上**，权威号没抽到
- `商户单号` 后面是 `4500…` → **匹配上了，把交易号当成商户单号**

第二个错更隐蔽：不是没抽到，是抽到一个**贴错标签**的号 → 判成 `MERCHANT_ORDER` → 非权威 → 退回文本指纹 → 90 天硬去重退化成 3 分钟。

**日志里只留「指纹 8a8b9c5a… 在去重窗口里，丢弃」，看起来完全正常。第 3 关从来没生效过，却没有任何一处会报错。**

### 现在的做法

先切成行，判定「这一行是不是干净的标签行」（整行等于标签，或标签 + `：` + 值），再按 **同行 → 上一行 → 下一行** 的优先级去邻域取值，值必须是整行纯字母数字。

同一行写法（银行 App 的 `交易单号：xxx`）继续支持——不能为了修微信改坏它。

**判据**：日志里走「指纹 … 丢弃」而不是「交易号 … 已经记过」，就要怀疑抽取环节压根没生效。这两条日志长得几乎一样。

## 4. 四道关卡

```
无障碍事件 → ① 形状闸 → ② 支付门 → ③ 解析 → ④ 交易号去重 → 草稿
```

| 关卡 | 文件 | 职责 |
|---|---|---|
| ① 形状闸 | `PaymentShape.kt` | 这屏是「一笔」还是「一屏记录」 |
| ② 支付门 | `PaymentGate.kt` | 像不像刚发生的一笔付款 |
| ③ 解析 | `LocalTextParser.kt` | 金额 / 方向 / 时间 / 商户 |
| ④ 交易号去重 | `PaymentId.kt` | 90 天硬去重 |

### ① 形状闸

数「带金额的短节点」。阈值 2：结果页 1 个放行，列表页 2~3 个挡下。

三类标签要分开，结论是相反的：

| 命中 | 屏 | 结论 | 动作 |
|---|---|---|---|
| 无标签金额 | 支付结果页 | **就是一笔** | 放行 |
| 构成项（实付/优惠/运费/合计） | 订单详情页 | **就是一笔** | 放行 |
| 账户状态（钱包/零钱/余额/额度） | 钱包页 | **一笔也没有** | 挡掉 |
| 促销位（免密/立减/满减） | 首页 banner | **不是消费** | 挡掉 |

### ② 支付门

判定顺序（顺序本身就是设计）：

1. 会话/消息列表页 → 挡（每条消息都自带完整金额和「成功」字样）
2. 付款确认页（`确认付款` 等，无完成措辞）→ 挡（证的是「打算付」不是「钱出去了」）
3. 有强动词（`支付成功` 等）→ 放行
4. 金额 ≥ 4 且无强动词 → 挡（像账单列表）
5. 促销词 → 挡
6. 弱动词 + 列表词 + 金额 ≥ 2 → 挡

**宁可放过，不可错杀**：放过的代价是一条用户看得见、点一下就能删的草稿；错杀的代价是这笔支付根本没被发现。

### ③ 解析

方向判定用**离金额最近的那个词**，不是整屏第一个命中的词。距离相同判支出（钱的默认归属是「我付出去了」）。

> 整屏扫 + 收入优先会出错：支付宝一屏 38 个节点里 `支出0.1元` 就贴在金额前面，
> 但只要**任意一个**节点出现「到账/退款/红包」，收入就先赢了。

### ④ 交易号去重

| 类型 | 权威 | 理由 |
|---|---|---|
| 微信 `交易单号` / `转账单号` | ✅ | 平台唯一，同一个号只可能是一笔 |
| 支付宝 `交易号` | ✅ | 同上 |
| `商户单号` | ❌ | 只在商户内部唯一，撞单号 = 静默丢账 |

窗口 90 天（不跟用户设置走），判据是硬 ID 而非文本哈希。

> 文本指纹把 8 位以上连续数字抹成 `#`——而交易号恰恰就是 8 位以上连续数字，
> 最有区分度的那段被亲手抹掉了。用户上周点开一笔 80 元账单、今天又点开，
> 两次归一化文本完全一样。

### 换机后必做

重装 App 会**禁掉**无障碍服务，且 `settings put secure enabled_accessibility_services` **不会自动恢复**：

```bash

### 已修复：商户抽取在真机读屏页上失效（2026-10-01）

金额、方向、时间一直是对的，**只有商户栏是脏的**，而商户栏正是历史统计和搜索
要用的字段。三处独立原因，都在 `LocalTextParser.guessMerchant`：

1. **按展示串反查金额行**。支付宝写的是 `支出10.1元`（尾零被它自己丢掉），
   而 `Money.toYuanDisplay(1010)` 是 `10.10`——两个字符串永远不相等，
   整屏 30 行里找不到金额行，商户直接返回 **null**。金额长什么样是对方 App
   决定的，拿自己的格式去反查，等于假设对方按你的格式写。
   改成按**数值**比（`amountMatches(line)` 取 minor 值）。
2. **从金额行一路向上扫到屏幕顶**。支付宝那一屏上方隔着二十行抽屉菜单，
   抓到了 `账单分类`。改成只在 ±2 行内找，且**先下后上**（真机详情页的
   商户标题渲染在金额下方；通知文本的商户在上方，两边都要覆盖）。
3. **认不出「字段的值」**。微信转账详情页长这样：
   ```
   等待对方确认收钱     ← 「当前状态」这个字段的值
   当前状态
   -0.10               ← 金额
   转账-转给橘生         ← 商户
   ```
   `等待对方确认收钱` 不含数字、不含货币符号、长度合规、不命中任何词表，
   所有过滤都拦不住它。节点顺序是**值在标签前面**（见第 3 节），所以
   唯一能认出它的办法是结构：**一行后面紧跟一行「纯标签」，它就是那个字段的值。**
   「纯标签」的判据是标签后面的内容剔掉分隔符后**什么都不剩**——
   不能用"不含数字"判，`当前状态 支付成功` 会被误判成纯标签，
   结果把下一行的真商户丢掉（第一版就是这么错的）。

回归用例在 `RealScreenMerchantTest`（11 条），含 3 条负例钉住老形状：
商户在金额**上面**一行（通知）、在金额**下面**一行（支付成功页）、
以及没有可信候选时宁可空着。

### 新增误判回归：微信账单列表页（`RealScreenFalsePositiveTest`）

```
2026年10月  支出 ¥0.10 收入 ¥0.00
转账-转给橘生        -0.10   10月1日 14:45
2025年9月   支出 ¥18.00 收入 ¥0.00
深圳市腾讯计算机系统有限…  -18.00  9月8日 09:24
…
```

**四笔独立交易**，每一行都长得像一条能读的账。危险在于它和详情页只差一次点击：
用户翻账单是常事，形状闸放过一次，账本里就会多出四条**过去几个月**的消费，
时间戳是旧的，事后极难察觉。形状闸和支付门两道都钉住了。

### 微信商家账单详情页：四道关卡全过的样本

```
product_SZ_2025080856740368 / 商户单号
42000028202508080433683194 / 交易单号          ← 值在标签前

解析结果：`-18.00 / 深圳市腾讯计算机系统有限公司 / 8月8日 09:24` 全对。

`PaymentId.valueNear` 正确认成了权威交易号（商户单号没有参与去重）。

### 未定论的观察

一条 `等待对方确认收钱` 的转账被记成了**支出**。钱还冻在零钱里，对方不收会退回。

倾向认为该记（钱确实主动转出去了），但**没验过**，不算结论。

### 被动 vs 主动

**微信这条路是被动的**——用户不点开账单详情页，就不会有这一笔。

> 2026-10-01 更新：原文这里写「支付宝、银行 App 的通知栏通路是主动的（它们发通知）」。
> 通知栏通路已整条删除，而支付宝实测也**不发支付通知**，所以现在**没有一条主动通路**。
> 全部自动记账都依赖用户主动点开账单详情页。

## 7. 验包的方法

`versionCode` 按天递增，**同一天出两次包 versionCode 完全相同**，装上也分不出来。md5 也不行（安装器会重排）。唯一硬证据是 dex 里的特征串：

```bash
adb shell pm path kapi.ledger.debug          # 拿路径
adb pull <路径> device.apk                   # 必须用 pull
# 解 zip 逐个 classes*.dex，utf8 解码后搜特征串
```

两条自检规则：

1. **必须 utf8 解码**。latin1 解出来是中文乱码，搜中文永远 0 命中，会误判成「装的是旧包」。
2. **必须带一条旧包也有的对照串**。对照串也 0 命中 = 脚本坏了，不是包旧了。没有对照的 0 命中不构成任何结论。

## 8. 事件类型与 API

```
adb shell am start -n com.tencent.mm/.ui.LauncherUI    # 拉前台，产生 WINDOW_STATE_CHANGED
adb shell monkey -p com.tencent.mm -c LAUNCHER 1        # ✗ 已在前台时不产生窗口切换
```

监听的三种事件：

| type | 常量 | 触发 |
|---|---|---|
| 32 | `TYPE_WINDOW_STATE_CHANGED` | 窗口切换 → 延迟重读 |
| 2048 | `TYPE_WINDOW_CONTENT_CHANGED` | 内容变化 |
| — | `TYPE_VIEW_SCROLLED` | 滚动 |

日志判读：

```
D/KapiA11y    事件 com.tencent.mm：type=32
D/KapiA11y    com.tencent.mm 形状像一笔：25 个节点，1 个带金额条目（-80.00）
I/AutoCapture 丢弃[A11Y/com.tencent.mm]：交易号 4500…（微信支付交易单号）已经记过，丢弃
W/KapiA11y    com.tencent.mm 不是一笔支付：整屏 2 个金额都落在账户状态或促销位上
```

**入口无条件留痕**（`traceThrottled`）。没有这一行，「微信屏蔽读屏」和「我们自己提前 return」在日志里完全同形。

**形状闸判定不节流**。上一版并进 `warnThrottled` 之后，「这一屏被判定成不是一笔」和「这一屏压根没读过」在日志里长得一模一样——那次漏记查了半天才发现不是没事件，是事件被吞了。

> 判据：任何 `warnThrottled` / `traceThrottled` 包住的东西，先问一句
> 「它被吞掉之后，我还能不能区分『没发生』和『发生了但没记』？」不能就拆开。
